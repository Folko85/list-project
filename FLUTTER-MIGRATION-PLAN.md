# Поэтапный переход с Java Spring Boot на Dart и Flutter

Цель — постепенно заменить веб-интерфейс AngularJS на Flutter Web и затем, если это по-прежнему подходит, перенести backend-функции на управляемую платформу авторизации и базы данных. После каждого этапа приложение должно оставаться доступным пользователям; старую реализацию не отключаем, пока новая не проверена.

| Этап | Что сделать | Как приложение остаётся рабочим |
|---|---|---|
| **1. Добавить Flutter Web как отдельное приложение** | Создать Flutter-клиент рядом с существующим backend. Настроить сборку и отдельный тестовый адрес или путь, не заменяя текущую стартовую страницу. | Существующий сайт остаётся основным; новая версия доступна отдельно для разработки и проверки. |
| **2. Подключить Flutter к существующему API** | Поэтапно перенести во Flutter регистрацию и вход, затем профиль и операции со списком задач. Использовать текущие API Spring Boot. SQLite, серверная авторизация и AngularJS пока остаются без изменений. | Оба интерфейса работают с одним backend и данными. Новую версию можно проверять на тестовых аккаунтах, не нарушая работу старой. |
| **3. Довести Flutter-клиент до функционального соответствия** | Сверить поведение с [обязательными сценариями](./FUNCTIONAL-SCENARIOS.md), добавить обработку ошибок и пустых состояний, проверить авторизацию и изоляцию данных. Включить новый интерфейс сначала для тестировщиков или небольшой группы пользователей. | AngularJS остаётся доступен для пользователей и для возврата в случае проблем. |
| **4. Подготовить управляемые авторизацию и базу данных** | Выбрать подходящую платформу с OAuth и управляемой базой данных; Supabase можно рассмотреть как один из вариантов. Создать целевую схему и настроить политики доступа на уровне базы (например, RLS). Проверить, что пользователь может работать только со своими данными. Не включать секретные серверные ключи в браузерную сборку Flutter. | Новую платформу сначала проверяют отдельно. Пользовательские версии продолжают работать через Spring Boot и SQLite. |
| **5. Перенести данные и определить привязку аккаунтов** | Перенести задачи, даты и принадлежность к пользователям; сверить число записей и владельцев. Определить подтверждённый способ связать прежние аккаунты с OAuth. Нельзя безопасно сопоставлять пользователей только по имени; текущие пароли нельзя автоматически преобразовать в учётные записи внешних OAuth-провайдеров. | До проверки переноса Spring Boot и исходная база остаются источником данных. Не вводить двойную запись без отдельного плана согласованности и отката. |
| **6. Переключить Flutter на новую платформу** | За переключателем конфигурации заменить в Flutter источник данных и способ входа: вместо Spring API использовать API выбранной платформы. Проверить OAuth, CRUD задач, запрет доступа к чужим данным и поведение при ошибках. | Сначала переключить тестовую среду или небольшую группу. Старый backend пока не удалять. |
| **7. Выполнить контролируемое переключение** | Создать финальную резервную копию и выбрать способ переноса последних изменений. При одноразовом переносе временно остановить запись, перенести оставшиеся изменения и переключить основной адрес на Flutter. Сохранить прежнюю базу и backend на ограниченный период отката; заранее определить, как обработать записи, созданные после переключения. | До переключения работает старая версия, после — новая. Откат возможен, пока определены и сохранены данные обеих систем. |
| **8. Удалить ставшие ненужными компоненты** | После подтверждения стабильной работы проверить журналы и убедиться, что старые интерфейс и API больше не используются. Затем отключить AngularJS и удалить Spring Boot, если он больше не нужен. Перед удалением отдельно решить судьбу Telegram webhook: Flutter Web его не заменяет; если бот понадобится, его обработчик должен жить в подходящем серверном или serverless-компоненте. | Старые компоненты удаляются только после завершённого переключения и проверки. При необходимости backend для оставшихся серверных функций сохраняется. |

## Важные условия перехода

- OAuth подтверждает личность пользователя, но сам по себе не защищает данные в базе. Доступ из браузера безопасен только при корректных политиках авторизации на серверной стороне или на уровне базы.
- Flutter Web — первый целевой клиент, выбранный для постепенной замены существующего веб-интерфейса. Поддержку Android и iOS можно планировать отдельно, после стабилизации веб-версии.
- На каждом этапе проверяются сценарии из [FUNCTIONAL-SCENARIOS.md](./FUNCTIONAL-SCENARIOS.md); переход к следующему этапу не должен лишать пользователя уже работающей функциональности.
- Не удалять старые приложение, API и исходную базу до проверки нового решения, восстановления из резервной копии и утверждённого плана отката.
